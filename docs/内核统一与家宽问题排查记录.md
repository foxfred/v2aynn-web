### 2026-10-01

**修复：家宽模式下国内站也走代理（连百度都打不开）**

选家宽节点后，百度这类国内站也被塞进了代理，还打不开。

根因在**订阅自己的规则**：

```yaml
rules:
  - GEOIP,LAN,DIRECT,no-resolve
  - GEOIP,CN,DIRECT,no-resolve   # ← 只看 IP，而且禁止解析
  - MATCH,🚀 节点选择
```

`GEOIP` 是**纯 IP 判据**，而浏览器经 HTTP / SOCKS 代理进来时内核只拿得到**域名**、
拿不到目标 IP；`no-resolve` 又明确禁止内核为了匹配规则去解析域名。两者叠加 ⇒
国内域名**一条都匹配不上** ⇒ 全部落到 `MATCH` 走家宽链。

在盒子上用一个极小的试验内核做了对照实验（只放 DIRECT 和 REJECT，落到 `MATCH`
就必然失败，一眼能看出走了哪条）：

| 配置 | 百度 | QQ | 内核实际匹配到的规则 |
| ---- | ---- | -- | -------------------- |
| 订阅原样（`no-resolve`） | 失败 | 失败 | `Match`（走代理）❌ |
| 只把 DNS 改成 redir-host | 失败 | 失败 | `Match`（走代理）❌ |
| 去掉 `no-resolve` | 200 | 302 | `GeoIP(CN) → DIRECT` ✅ |
| **加一条 `GEOSITE,cn,DIRECT` 在最前** | 200 | 302 | `GeoSite(cn) → DIRECT` ✅ |

顺带排除了一个直觉上的误判：**改 DNS 模式（fake-ip → redir-host）没用**，
问题出在规则本身。

**修法**：在家宽配置的 `rules:` 段最前面**新增一条** `GEOSITE,cn,DIRECT`。

- **纯新增**：订阅原有的规则一条没改、没删；`proxies` / `proxy-groups` 一个字节没动，
  家宽链（openvpn 的 `dialer-proxy` 指向策略组）完全不受影响
- 用 `GEOSITE`（按域名判断）而不是给 `GEOIP,CN` 去掉 `no-resolve`：后者要靠 DNS
  解析结果判断，而解析用的是订阅里写的国内 DNS，外国域名可能被解析成被污染的
  国内 IP，反而把该走代理的站点误判成直连
- 缩进跟着订阅走，找不到 `rules:` 段时原样返回（宁可不改，也不凭空造规则段）
- 幂等：重复改写不会不断往里加规则

**修复：家宽节点列表把明明测通的节点显示成「超时」**

家宽节点除了 `select` 组，还挂在订阅的 **`🏠 家宽自动`（type: fallback）** 组下。
fallback 组会**主动做整组健康检查**，而 mihomo 的整组检查**没有并发限制** ——
它会把几十个节点一次性全打出去，而这些家宽节点的出口又全挤在**同一条前置通道**里，
一挤爆就大批失败。盒子实测确认：**失败的健康检查会往该节点的 history 里写一条
`{"delay":0}`**。

而列表接口里，内核的 history 原本会**无条件覆盖**我们自己扫描出的延迟：

```go
if d, ok := live[n]; ok {
    if d > 0 { ping = d } else { ping = -1 }   // ← 内核那条 0 把 480ms 盖成了「超时」
}
```

**修法**：内核的记录只在**确实测到延迟（>0）**时才覆盖。我们自己的扫描是
**限并发 4 + 每节点错峰 0–200ms** 的，对家宽链比内核那种「整组一次性全打出去」
更可信，所以内核的 0 / 负数只当作「没有可用信息」。

**其它**

- 新增单测 10 项：`TestInjectCNDirectRule*`（4 项：幂等 / 跟随缩进 / 无 rules 段 /
  空 rules 段）、`TestClashNodePingKernelZeroDoesNotOverrideStored`（6 个边界），
  并给 `TestParseRealSubscription` 加了「真订阅改写后第一条规则必须是
  `GEOSITE,cn,DIRECT`」的断言 —— 防止「样本里对、真订阅里不对」
- 界面**一个像素都没动**，不加任何开关

**真机验收（2026-10-01 深夜，盒子实测）**

不用切换当前连接，直接拿**测速探针内核**当试验台 —— 它跑的就是家宽配置（含改写后的规则），
自己监听一组临时端口：

| 经探针内核访问 | 结果 |
| -------------- | ---- |
| `https://www.baidu.com` | HTTP 200 / **0.227 秒** |
| `https://www.cloudflare.com/cdn-cgi/trace` | HTTP 200 / **5.03 秒** |

差 22 倍。再翻内核的连接表，两条路径的归属一目了然：

- 百度 → `rule: GeoSite / cn`，`chains: ["DIRECT"]`（直连，不碰代理）
- cloudflare → `rule: Match`，`chains: ["🏠 JP-家宽-17", "🏠 家宽自动", "🚀 节点选择"]`（走家宽链）

家宽节点列表也恢复显示实测延迟（不再是满屏「超时」）。

**重大变更：内核统一 —— 普通节点也交给 mihomo，xray 退役**

以前是双内核：普通节点走 xray，家宽节点走 mihomo，两个内核抢同一组端口、同一时刻只能跑一个。
现在**只剩一个内核 mihomo**，程序按你点的节点类型自动加载对应配置（普通节点用程序现场生成的
Clash 配置，家宽节点用订阅原文），界面上依然没有内核开关。

- 用户视角**没有任何操作变化**：照旧点节点即可，点哪种就自动换哪份配置
- 收益：少一份内核文件的部署负担，少一处「现在到底谁在跑」的判定分歧，
  测速时也不再需要「先把家宽切上来」
- xray 的代码与二进制**暂时保留作回滚保险**，稳定观察一段时间后再清理

**新增：普通节点自动故障转移（mihomo 版）**

改成 mihomo 之后，普通节点的配置里**只有一个 select 组，它不会自己换节点** ——
xray 时代靠「节点不通 → 进程起不来 → 崩溃 4 次 → 换节点」的触发链在 mihomo 下根本不存在
（内核加载配置时不校验节点能不能连），于是「选的节点挂了会自动换」这个能力**丢了**。这次把它补回来：

- 程序**每 30 秒**经内核控制口探一次当前普通节点（内核直连节点，不受分流规则影响）
- **连续 3 次**失败才判定为坏（避免网络抖动误判）；只要成功一次就清零
- 换节点按「已测速可达优先 → 延迟升序」挑，排除当前节点和已经试过的节点
- 最多试 8 个；全试完仍不可用就放弃，等下一轮订阅刷新
- 复用设置里原有的「自动故障转移」开关，**没有新增任何开关**；
  家宽模式不启用它（订阅自带 url-test 自动组，内核自己会换）

真机验收（2026-10-01）：故意切到一个不可达的节点，**65 秒后程序自己换走了**，
换到的节点出口 IP 正常可用；部署后首次启动也自然命中过一次真实故障转移
（原节点真的挂了，97 秒后自动换上可用节点）。

**其它**

- 设置页底部那段「家宽走 mihomo、普通节点走 xray」的说明已按统一后的实际情况改写
- 新增 `internal/mihomo/failover_test.go`（9 项）与 `internal/config/failover_test.go`（3 项）

**修复：家宽测速「测不了、数字乱、记错节点」**

你反馈的三个现象，其实是三个独立的毛病叠在一起：

| 你看到的 | 真正的原因 |
| -------- | ---------- |
| 连着 xray 时测不了家宽节点 | 两个内核抢同一组端口，同一时刻只能跑一个；测速又绑死在「先把家宽切上来」 |
| 测出来的速度完全乱 | 内核把整组 76 个节点**一起**打出去，而家宽出口全挤在**同一条前置通道**里，互相挤爆 |
| 不知道哪个节点能用 | 家宽节点没有地方存测速结果，速度被记到了别的节点头上 |

**一、新增「测速待命内核」，跨内核也能测**

- 程序会另外起一个**只用来测速**的小内核，跑在**备用端口**上（系统自动挑 4 个空闲端口，只监听本机）。
  它不承载你的流量，所以**连着普通节点照样能测家宽**，测速不会打断当前连接
- 这个待命内核有**自己独立的工作目录**（`dataDir/probe/`），不和正在服务流量的内核抢运行配置
- **内存自适应**：读 `/proc/meminfo` 判断可用内存，低于 150MB 时改成「用完就收」，测完立刻把内存还回去；
  盒子内存够就常驻，省掉每次测速的启动等待。内核正在跑家宽（即你正连着家宽）时也不会另起待命内核 —— 直接用正在跑的那个测

**二、测速改成「限并发 + 每个节点随机错峰」**

- 以前内核的测速接口会把整组节点**一次性并发全打出去**，而所有家宽节点的出口都塞在**同一条前置通道**（`dialer-proxy`）里，
  一挤爆就大部分超时（-1）、少数延迟巨大且随机 ⇒ 就是你看到的「数字乱」
- 现在改成**一次最多测 4 个**，排着队来，测出来的数字才反映真实链路
- 每个节点开测前**随机等 0–200 毫秒**错峰（对齐 Clash Verge 的做法），避免几个节点同时去抢同一条通道
- 首次握手延迟 ≠ 真实延迟：家宽节点第一次请求要现场建 OpenVPN 隧道（常常好几秒），
  所以**复测一次取较小的值**；已经确定测不通的节点不再复测（省掉白等的一次超时）

**三、测速结果存到正确的节点上**

- 家宽分组的节点列表是**空的**（节点整份交给内核管），所以 `Node.Ping` / `Node.Speed` 没有地方安放，
  以前只能写回「当前激活节点」—— 而家宽模式下那个字段还停在上一个普通节点上，
  于是家宽测出来的速度被记到了普通节点头上
- 新增 `Group.Probes` 一张表（按节点名索引），专门存家宽节点的延迟与速度，界面刷新后仍能看到上次结果

**四、修掉「家宽测速后按延迟排序不管用」**

- 排序是**服务端做的**（右上角下拉框只发一次请求，然后重拉列表）。
  但家宽分组的节点列表走的是另一条代码路径，那条路径**压根没读排序设置**，
  还把「当前排序方式」写死成空 —— 所以在家宽分组上点「延迟↑ / 延迟↓」没有任何反应
- 现在家宽分组与普通节点走**同一个排序规则**：延迟数值有效的排前面（升序/降序都支持），
  测过但不通的（显示「超时」）和从没测过的一律沉到列表底部
- 整组测速完会自动按当前排序重排，不用手动再点一次

**其它**

- 界面**一个像素都没动**，不加任何开关
- 新增 `internal/mihomo/prober.go`（待命内核 + 限并发测速）与对应单测 9 项、家宽通道单测 7 项
- 新增排序回归测试 1 项（已确认：去掉修复后该测试会失败）

**五、修掉「网关检测不稳定」—— 三处偏离客户端标准做法的地方**

对照原作（cfnew 家宽）的官方说明与 Clash 客户端（Clash Verge Rev）的实现，
逐行核了 mihomo 内核源码（v1.19.31），发现我们的做法有三处偏离：

| 问题 | 后果 |
| ---- | ---- |
| 测速地址**硬编码成 `http://`**，而订阅自己写的是 `https://` | 数字忽大忽小、时有时无 |
| 「前置通道检测」拿**策略组名**去测，内核会落到「成员列表第一个节点」且不看它死活 | 那个节点恰好挂着就误报「前置不通」，另外两百多个明明好好的 |
| 没有随机错峰，几个节点同时去抢同一条通道 | 测出来的是互相踩踏的噪声 |

**1. 测速地址改成从订阅里读**

- 订阅里每个策略组自己写了测速地址（cfnew 写的是 `https://www.gstatic.com/generate_204`），
  程序现在**优先用它**，读不到才退回默认值，而默认值也是 `https://`
- 为什么必须 https：订阅开了 `unified-delay` 时，内核会对同一个地址**连发两次 HEAD 请求**；
  地址是 `http://` 时官方源码会打印
  `It is recommended to use HTTPS ... using HTTP may result in failed tests`
- 附带好处：订阅换了测速地址，程序自动跟着换，不用改代码

**2. 去掉「前置通道门禁」，改成拿真实家宽节点判断前置好不好**

- 以前是「先探一次前置通道，不通就直接返回」。问题在于拿**组名**去测时，
  内核走的是组的 `fast()`，而它在组里还没有延迟历史时**无条件取成员列表的第一个节点、
  且不检查它死活** —— 于是「探前置通道」实际变成了「探订阅里第一个 CF 节点」。
  它恰好挂着就误报「前置不通」；订阅一刷新节点顺序变了，同一个分组又时好时坏
- 现在判断前置好不好的**依据也换了**：不再看前置节点自己访问 gstatic 快不快
  （那个指标与「能不能承载一条 OpenVPN 长连接」毫无关系），
  而是**抽几个真实家宽节点实际连一下** —— 样本里至少一半能连通才算这个前置够用（见第六条）
- 抽样是**等距取样**的：订阅里节点按地区聚堆排（「🏠 JP-家宽-01…JP-家宽-20」挨在一起），
  取前 8 个可能全落在同一个国家的同一个服务端上，那一批集体掉线会被误判成「前置不通」

**3. 每个节点开测前随机错峰 0–200 毫秒**

- 对齐 Clash Verge Rev 的做法（它也是逐节点测、并发上限 10、每个节点前随机等 0–200ms）
- 代价只是整轮多花几百毫秒，换来的是并发的那几个节点不再同时抢通道

**新增测试**

- `TestPingClashGroupNotBlockedByFrontProbe`：家宽节点能测通时，绝不能因为前置探测把结果挡掉
  （**已确认：装回旧逻辑后该用例失败**，报的就是那句误报的「前置通道不通」）
- `TestPingClashGroupKeepsFrontWhenItWorks`：前置本来就是好的时候，一次都不许动它
- `TestTestURLOf*` / `TestDefaultTestURLIsHTTPS`：测速地址必须跟着订阅走、兜底必须是 https
- `TestSweepDelayAppliesJitterBeforeEachMeasure`：错峰确实每个节点都做了一次
- `TestCountAlive*`（5 项）：抽样判活的边界（数够就收工、全不通为 0、不超过上限、空样本、限并发）

**六、修掉「测出来的活节点，选上没一会儿就全失效了」**

这是本轮的**主修复**。你反馈的「家宽测速测出来的活链接，选用后一会儿就会失效，
再测全部家宽都是超时」，根因不在节点本身，而在**家宽链的第一跳 —— 前置通道**。

**家宽链是三层结构：**

```
你 → mihomo → ⚡ CF前置（选中的那 1 个 CF 节点）→ VPN Gate 家宽服务器
                    ↑
          70 多个家宽节点全部挤在这同一个出口上
```

也就是说：**前置通道选错一个节点，70 多个家宽节点会一起陪葬。**

**为什么会选错**

`⚡ CF前置` 在订阅里是一个 `url-test` 组，内核按「它自己访问 gstatic 快不快」来自动挑。
问题是**这个指标与「能不能承载一条 OpenVPN 长连接」毫无关系**。在盒子上拿同一批家宽节点、
只换前置做了对照实验：

| 前置节点 | 它自己访问 gstatic | 家宽节点通过率 |
| -------- | ------------------ | -------------- |
| `联通-09` | **171ms（更快）** | **1 / 4** |
| `优选域名-01` | 197ms（稍慢） | **3 / 4** |

更糟的是：订阅里没写 `lazy`，而 mihomo 的默认值是 `lazy: true` ——
意思是**只有有流量经过该组时才做健康检查**。前置组只被 `dialer-proxy` 间接引用、没有直接流量，
所以**健康检查几乎不跑**。盒子实测：`⚡ CF前置` 的 216 个成员最后一次健康检查停在 `01:04`，
此后 **10.5 小时再没检查过一次**，一直卡在那个「延迟最低但跑不了家宽链」的节点上。

**现在的做法：测速时自动挑一个能跑通家宽链的前置**

1. **先体检**：整组测速之前，等距抽 8 个家宽节点实际连一下。样本里**至少一半**能连通
   ⇒ 前置够用，照常测
2. **不行就换**：不到一半时，按内核记录的延迟从低到高挑候选（明确测过不通的跳过），
   逐个换上去重试，最多试 5 个
3. **找到就固定**：一旦某个候选能让家宽节点连通，就把它固定住（内核侧 `ForceSet`），并**写进配置**
4. **换不成也如实说**：试遍候选都不行时，把前置拨回原来那个，并告诉你「试过哪些、都不行，
   大概率是这批节点集体掉线，点『更新』换一批」—— 不再甩一句笼统的「全部超时」

**判据是「比例」不是「有没有」**

一开始的判据是「样本里有一个通就算前置可用」，这个门槛太松，修复在最常见的场景下等于没生效。
盒子实测同一批 6 个样本：

| 前置 | 样本通过率 | 整组 65 个测出几个 |
| ---- | ---------- | ------------------ |
| `联通-01`（内核自动挑的） | **0 / 6** | **6 个** |
| `优选域名-01` | 2 / 6 | — |
| `优选域名-03` | 4 / 6 | — |
| `优选域名-04` | **5 / 6** | **38 个** |

「勉强有 1 个通」和「能承载大半样本」对用户的差别，是「测出 6 个节点」和「测出 38 个节点」。
所以门槛定在**样本的一半**（8 个样本 → 4 个）。

**为什么必须写进配置（这一步是「选上没一会儿就失效」的关键）**

测速时通常是**测速待命内核**在干活（你还连着普通节点，家宽内核根本没启动）。
而你点了某个家宽节点之后，真正跑起来的是**家宽内核** ——
它启动时会自己按 `url-test` 给前置组挑一个（判据又是错的），于是
「测速时明明好好的，选上没一会儿就失效」。

所以换好的前置会记在分组配置里（`frontNode` 字段），**内核每次启动时重新应用一遍**。
这样测速和实际使用用的是同一个前置。

**★ 内核的「固定」只是偏好，不是强制**

这是本轮最后一个、也是最隐蔽的坑。逐行核 mihomo v1.19.31 源码
（`adapter/outboundgroup/urltest.go`）才看清 `url-test` 组的真实语义：

```go
func (u *URLTest) fast(touch bool) C.Proxy {
    if u.selected != "" {                              // u.selected = 我们固定的那个
        for _, proxy := range proxies {
            if !proxy.AliveForTestUrl(u.testUrl) { continue }   // 不活就跳过
            if proxy.Name() == u.selected { return proxy, nil }
        }
    }
    ... 回退到「延迟最低的活节点」；一个活的都没有就用成员列表第一个
}
```

也就是说：**被固定的节点如果在内核自己的账本里是「不活」，内核会静默忽略我们的固定值**、
继续用它自己挑的那个。而那条判据（能不能直接访问订阅里写的那个测速地址，一般是 gstatic）
**与「能不能承载一条 OpenVPN 长连接」完全是两回事** —— 正是这个错配本身。

盒子实测（216 个 CF 前置）：PUT 过去后大约**一半**的节点 `now` 纹丝不动，
它们的延迟测试直接返回 `503`。所以：

- **换候选时必须确认那次切换真的生效了**（读一次内核的 `now`），否则
  「换上前置 c → 量样本」量到的其实是内核回退后仍在用的那个节点，
  候选之间的比较全成噪声 —— 于是一个真正能用的前置可能被判成「没用」而放弃
- 内核一个候选都没采用时，提示语如实说「内核一个都没采用」，而不是含糊的「都没更好」——
  两者的处理建议完全不同（前者得换一批**前置**，后者是换一批**家宽节点**）
- 内核启动重放前置之后也读一次 `now` 核实，不一致就往日志里写一行告警，
  免得「明明固定了却没生效」变成查不出来的悬案

**真机验收（2026-10-01）**

把盒子切到家宽节点、让**内核**真的跑起来，读它的前置组：

```
配置里记录的 frontNode = ['优选域名-27']
内核前置组  now = 优选域名-27   fixed = 优选域名-27   成员 216 个

```
