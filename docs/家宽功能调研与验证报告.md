> **日期**：2026-09-30

## 一、结论摘要

1. **xray 内核无法实现家宽功能**。xray 没有 openvpn 出站协议，也没有 `dialer-proxy`
   的等价能力。cfnew 家宽的唯一实现路径是 **mihomo 的 `type: openvpn` + `dialer-proxy`**。
   ⇒ **「多内核」不是可选项，是必需项。**
2. **技术上可行，且已在真机验证通过**。mihomo v1.19.31（满足 cfnew 要求的 ≥1.19.25）
   在目标盒子上成功运行，家宽链打通，**出口 IP 确认为韩国住宅宽带**。
3. **盒子资源充足**。911 MB 内存 / 剩余 313 MB；mihomo 完整启动后 RSS ≈ 67 MB。
4. **实施有一条低成本路径**（路线 C），约 300~500 行新增代码，现有 xray 逻辑零改动。

## 二、cfnew v3.1 的「家宽链式」是什么

**链路结构（三层嵌套）**：

```
普通模式：  设备 ──→ xray ──→ 节点服务器 ──→ 目标站

家宽模式：  设备 ──→ mihomo ──→ CF 边缘节点 ──→ VPN Gate 住宅宽带 ──→ 目标站
                            ↑            ↑                  ↑
                         本地内核    dialer-proxy 承载    真正的出口(住宅 IP)
```

- **机制**：OpenVPN 出站 + `dialer-proxy` 指向 CF 节点组，把 OpenVPN 的握手与传输
  **整个塞进 CF 通道**走
- **订阅地址**：`https://<域名>/<UUID>/sub?target=vg`（未开启家宽返回 403）
- **格式**：只输出 Clash（Stash / Surge / sing-box 均不支持）
- **节点来源**：VPN Gate 志愿者共享节点

**官方自述的限制**：

| 限制 | 实际影响 |
|---|---|
| 节点掉线是常态，约一半能通 | 必须靠 fallback 组自动切换 |
| 只支持 TCP（节点标 `udp: false`） | 走该节点的 UDP 流量不可用 |
| 速度取决于对方家庭上传带宽 | 不保证速度 |
| 节点源拉不到时订阅返回 503 | 客户端保留上一份配置 |

## 三、订阅实测（脱敏）

抓取结果：**直连可访问**（HTTP 200，约 114 KB），是**完整 Clash 配置**而非纯节点列表。

| 顶层键 | 值 |
|---|---|
| `mixed-port` | 7890 |
| `allow-lan` | false |
| `mode` | rule |
| `external-controller` | 127.0.0.1:9090 |
| `dns` | fake-ip，223.5.5.5 + 1.1.1.1 |
| `proxies` | **287 个** |
| `proxy-groups` | 4 个 |
| `rules` | 3 条 |

**节点构成**：`trojan` 144 + `vless` 72 + **`openvpn` 71**

**openvpn 节点结构**（关键）：

```yaml
type: openvpn
server: <VPN Gate 住宅节点 IP>
port: 1776
proto: tcp                    # 走 TCP，印证「只支持 TCP」
udp: false
cipher: AES-128-CBC
auth: SHA1
ca / cert / key               # 内嵌证书，每节点约 4.6 KB
username / password           # auth-user-pass 认证
dialer-proxy: "⚡ CF前置"      # ★ 指向 url-test 策略组
remote-dns-resolve: true
dns: [8.8.8.8, 1.1.1.1]
handshake-timeout: 30
```

**策略组结构**：

| 组名 | 类型 | 成员数 | 说明 |
|---|---|---|---|
| `⚡ CF前置` | url-test | 216 | 144 trojan + 72 vless |
| `🏠 家宽自动` | fallback | 71 | `lazy: true`，1800s 间隔 |
| `🏠 家宽节点` | select | 71 | |
| `🚀 节点选择` | select | 4 | **第一项就是 `🏠 家宽自动`** |

**关键设计含义**：

1. `dialer-proxy` 指向的是**策略组**而不是单个节点 ⇒
   **必须完整保留 `proxies` + `proxy-groups` 结构**。只提取 `proxies` 会让
   `dialer-proxy` 指向不存在的组，**整条家宽链静默失效**。
2. `rules` 末条是 `MATCH,🚀 节点选择`，而该组第一项是 `🏠 家宽自动` ⇒
   **默认全部流量走家宽出口**，无需手动切换。
3. 需改写的**只有 5 个顶层键**（删 `mixed-port`，加 `port`/`socks-port`/`tproxy-port`，
   `allow-lan` 改 true）。这些键全部位于文件头部且是顶层简单键 ⇒
   **可用行级替换实现，不必引入 YAML 解析库，「零外部依赖」特性可保住**。

### 4.3 实测中发现的坑（实施时必须处理）

#### ★ 坑 1：geo 数据是硬依赖，缺失会导致启动阻塞

mihomo 若找不到 GeoIP 数据库会**自动从 GitHub 下载**，墙内超时（90 秒）后
**整个服务卡死在初始化阶段，代理端口完全不监听**。

```
INFO  Can't find MMDB, start download
ERRO  can't initial GeoIP: can't download MMDB: context deadline exceeded
configuration file test failed
```

**必需文件**（放在 `-d` 指定的工作目录下）：

| 用途 | 文件名 | 体积 | 默认下载地址 |
|---|---|---|---|
| MMDB | `geoip.metadb` | 8.0 MB | `.../meta-rules-dat/releases/download/latest/geoip.metadb` |
| geosite | `geosite.dat` | 4.1 MB | `.../latest/geosite.dat` |
| （备）geoip | `geoip.dat` | — | `.../latest/geoip.dat` |
| （备）ASN | `GeoLite2-ASN.mmdb` | — | `.../latest/GeoLite2-ASN.mmdb` |

> **与 xray 的本质区别**：xray 缺 `geoip.dat`/`geosite.dat` 只是分流规则失效，
> 代理照常工作；**mihomo 是启动即阻塞**。分发时必须把 geo 数据当作**必需依赖**
> 与内核一起打包，不能假设它会自己下载。

#### 坑 2：必须显式指定 `-d` 工作目录

不传 `-d` 时 mihomo 回落到默认目录（`~/.config/mihomo`），放在项目目录下的
geo 数据就找不到，表现为 `-t` 检查失败并报 `MMDB invalid, remove and download`。
**传了 `-d` 后一切正常**。

#### 坑 3：日志刷屏

默认 `log-level: info` 下，家宽节点的 DNS 查询会疯狂打日志：

```
[UDP] mihomo --> 1.1.1.1:53 doesn't match any rule using 🏠 KR-家宽-08
```

建议设 `log-level: warning` 或 `error`。

#### 坑 4：节点掉线是常态

```
[OpenVPN](🏠 JP-家宽-02) error reading packet from OpenVPN link: ws closed: 1005
```

`ws closed: 1005` 大量出现，与 cfnew 自述的「约一半能通」一致。这是该功能的
固有特性，不是配置错误。

### 4.4 复测结果与稳定性观察（22:19）

#### ✅ 验证了一条实现细节

`-t` 配置检查**必须带 `-d`**，带上后立即通过（195 ms）：

```
./mihomo -t -d /tmp/mt -f config.yaml
INFO Initial configuration complete, total time: 195ms
configuration file /tmp/mt/config.yaml test is successful
```

这证实了上面坑 2 的判断：**失败原因是不传 `-d` 时工作目录回落**，与 geo 文件本身无关。

#### ⚠️ 出口 IP 复测失败（首测成功后约 3 分钟）

```
curl -x http://127.0.0.1:17890 https://www.cloudflare.com/cdn-cgi/trace
（无任何输出）

curl: (35) TLS connect error: error:0A000126:SSL routines::unexpected eof while reading
下载速度: 0.00 Mbps
```

**判断：这是家宽节点掉线，不是配置错误。** 依据三点：

1. 同一份配置在 22:16 首测时成功（出口为韩国 SK Broadband 住宅宽带）
2. 首测日志中已出现大量 `ws closed: 1005`
3. 与 cfnew 官方自述「节点掉线是常态，实测约一半能通」完全一致

#### ★ 实施时必须关注的可用性问题

`🏠 家宽自动`（fallback 组）的配置是 **`interval: 1800`（30 分钟）+ `lazy: true`**。

`lazy: true` 意味着**不使用时不主动测速**，而 `interval` 长达 30 分钟 ⇒
**节点掉线后，健康检查可能要很久才触发切换**，直接影响可用体验。

实施路线 C 时应考虑：

- 缩短 `interval`（例如 300 秒），或
- 关闭 `lazy`，让 fallback 组持续探测

> ⚠️ 注意：这是**改动 cfnew 生成的配置**，需评估是否偏离其设计意图。
> 也可先保持原样，实测体验后再决定。

#### 速度仍待测

因复测时链路不通，**下载速度未取得有效数据**。这是本次验证唯一的空缺项。

## 五、三条实施路线

| 路线 | 做法 | 改动量 | 风险 |
|---|---|---|---|
| **C. 独立 mihomo 模式** | xray 逻辑一行不动，新增 mihomo 内核管理器；拉家宽订阅 → 注入我方端口 → 启动；节点切换/状态走 external-controller API | 约 300~500 行 | **最低** |
| **A. 双内核自动路由** | 订阅分组加「类型」字段，普通订阅走 xray、家宽订阅走 mihomo | 约 700~1000 行 | 中 |
| **B. mihomo 全量替代 xray** | 一套内核统一处理 | 1500+ 行 | **高**，现有节点需全部重新验证 |

**推荐 C → A 渐进**：先用 C 跑通并观察稳定性，再决定是否升级。

### 路线 C 的实现要点

1. **拉订阅**：复用现有 `fetchOne`，但 UA 要伪装成 Clash（cfnew 按 UA 返回格式）
2. **写配置**：**最小改写** cfnew 的完整配置 —— 保留其 `proxies` / `proxy-groups` /
   `dialer-proxy` 结构（不解析、不理解），只替换顶层端口键
3. **启动**：`mihomo -d <dataDir> -f <config>`，geo 数据预置在 `<dataDir>` 下
4. **节点列表/切换/测速**：走 `external-controller` API
   （`GET /proxies`、`PUT /proxies/{name}`、`GET /proxies/{name}/delay`）
5. **端口映射**：`port`→10810(HTTP)、`socks-port`→10808(SOCKS5)、
   `tproxy-port`→12345(透明代理)、`allow-lan: true`
